depth/

The problems I keep coming back to

Staff and research tracks both reward going deep on a small set of hard problems rather than wide on many easy ones. These are the four I gravitate toward, each grounded in something I've actually shipped — not a reading list.

01 · correctness under partial failure

What happens when a step in the pipeline lies?

Sub-second theft/anomaly alerting only works if you've decided, precisely, what a false signal costs versus a missed one — and tuned the pipeline to that trade-off, not to a vague "be accurate" goal.

Kafka state-store alerting pipeline, <3% false-positive rate
02 · config as the unit of change

When should a change be a deploy, and when should it be data?

The moment a rule changes more often than the code around it, the rule belongs in config — that line is where a versioning framework either scales with an org or becomes its own bottleneck.

51 state leave policies, versioned by effective date, zero code changes
03 · scaling without re-architecting

Which decisions today make 3× growth a non-event?

The interesting design work isn't handling today's load — it's picking the primitives (partitioning, idempotency, state ownership) that let tomorrow's 3× land on the same architecture.

Kafka + PostgreSQL device sync, 3× fleet growth, zero re-architecture
04 · event-driven consistency

What's the honest consistency model of this pipeline?

"Eventually consistent" is only a good answer once you can say exactly how long "eventually" is, and what a consumer should do in the meantime — that's a design decision, not a disclaimer.

Kafka Streams enrichment, PostgreSQL system of record, 7→20 msg/sec
