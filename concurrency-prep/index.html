How a thread pool works

Creating an OS thread costs roughly 0.5–1 MB of stack and a syscall. If every request spawned one, a traffic spike would exhaust memory and the CPU would spend its time context-switching. A thread pool fixes this by keeping a fixed set of long-lived worker threads and a queue of tasks. Callers submit tasks. Workers loop forever: take a task, run it, take the next. It gives you three things: thread reuse, a bound on concurrency, and a place to apply backpressure when the system is overloaded.

Producers never run the work themselves. The queue decouples submission from execution, and its capacity is your backpressure knob.

What ThreadPoolExecutor.execute() actually does

Interviewers love this because most people get it wrong. The order is core threads, then queue, then extra threads, then reject. Not “grow to max first”.

  1. If fewer than corePoolSize workers are running, start a new worker with this task as its first task. This happens even if other workers are idle.
  2. Otherwise, workQueue.offer(task). If it succeeds, re-check the pool state. If the pool was shut down in between, remove the task and reject it. If zero workers are alive, start one.
  3. If the queue is full and fewer than maximumPoolSize workers exist, start a non-core worker for this task.
  4. Otherwise call the RejectedExecutionHandler: AbortPolicy (throw, the default), CallerRunsPolicy (the submitting thread runs it, which slows producers down as natural backpressure), DiscardPolicy, or DiscardOldestPolicy.

Each worker runs runWorker(): loop on getTask(), which calls queue.take() for core workers and queue.poll(keepAliveTime) for non-core ones. A non-core worker that times out returns null and exits, so the pool shrinks back to core size. Pool state and worker count are packed into one AtomicInteger ctl: the top 3 bits hold the run state (RUNNING, SHUTDOWN, STOP, TIDYING, TERMINATED) and the low 29 bits hold the count, so both can be updated with a single CAS.

The classic trap. With an unbounded LinkedBlockingQueue, step 2 never fails, so the pool never grows past corePoolSize and maximumPoolSize is ignored. That is exactly what Executors.newFixedThreadPool gives you, and a slow downstream turns it into an OutOfMemoryError. newCachedThreadPool has the opposite problem: a SynchronousQueue and unbounded max threads. In production, build the ThreadPoolExecutor yourself with a bounded queue and a named ThreadFactory.

Sizing

From Java Concurrency in Practice: threads = Ncpu × Ucpu × (1 + W/C), where W/C is the ratio of wait time to compute time. CPU-bound work: about Ncpu + 1. A task that waits 90 ms on I/O for every 10 ms of CPU on an 8-core box: 8 × (1 + 9) = 80 threads. Then measure, because the downstream (a DB connection pool of 20) is often the real limit.

Pitfalls to name in an interview

  • Swallowed exceptions. submit() stores the exception in the Future. If nobody calls get(), it disappears. execute() lets it reach the thread's UncaughtExceptionHandler and kills that worker, which is then replaced.
  • Pool-induced deadlock. A task in a bounded pool submits a subtask to the same pool and blocks on it. When every worker does this, nobody is left to run the subtasks.
  • ThreadLocal leaks. Workers live forever, so a ThreadLocal set by one task is still there for the next. Always clear in finally.
  • Virtual threads (Java 21). Don't pool them. Use Executors.newVirtualThreadPerTaskExecutor() and limit concurrency with a Semaphore. Watch for pinning inside synchronized blocks on JDK 21–23.
Java · minimal pool 
public final class SimplePool {
  private final BlockingQueue<Runnable> queue;
  private final List<Thread> workers = new ArrayList<>();
  private volatile boolean shutdown;

  public SimplePool(int n, int capacity) {
    queue = new ArrayBlockingQueue<>(capacity);
    for (int i = 0; i < n; i++) {
      Thread t = new Thread(this::loop, "worker-" + i);
      workers.add(t);
      t.start();
    }
  }

  public void execute(Runnable r) {
    if (shutdown) throw new RejectedExecutionException();
    if (!queue.offer(r)) throw new RejectedExecutionException("full");
  }

  private void loop() {
    try {
      while (!shutdown || !queue.isEmpty()) {
        Runnable r = queue.poll(100, TimeUnit.MILLISECONDS);
        if (r == null) continue;
        try { r.run(); }
        catch (Throwable t) { /* log, keep worker alive */ }
      }
    } catch (InterruptedException e) {
      Thread.currentThread().interrupt();
    }
  }

  public void shutdown() { shutdown = true; }
  public void shutdownNow() {
    shutdown = true;
    workers.forEach(Thread::interrupt);
  }
}

This has a real race between the shutdown check in execute() and the isEmpty() check in loop(): a task can be accepted after every worker has exited. Finding and fixing it is part of Module 3.

Go · worker pool 
func Pool(ctx context.Context, n int,
    jobs <-chan Job) <-chan Result {

  out := make(chan Result)
  var wg sync.WaitGroup
  for i := 0; i < n; i++ {
    wg.Add(1)
    go func() {
      defer wg.Done()
      for {
        select {
        case <-ctx.Done():
          return
        case j, ok := <-jobs:
          if !ok {
            return // producer closed jobs
          }
          select {
          case out <- process(j):
          case <-ctx.Done():
            return
          }
        }
      }
    }()
  }
  go func() { wg.Wait(); close(out) }()
  return out
}

Goroutines start at about 2 KB and are scheduled onto OS threads by the runtime (the M:N “GMP” scheduler), so Go doesn't need a pool for reuse. You use one to bound concurrency against a limited resource. Closing jobs is the equivalent of shutdown(), and cancelling ctx is shutdownNow().

Type A

Ordering and signalling

Worked problem

N threads, round robin. Start N threads. Together they print 1 to MAX, where thread i prints the numbers with (n − 1) % N == i, strictly in order. Every thread must exit when printing is finished.

Show solution

Use one lock and one Condition per thread, so each print wakes exactly the thread whose turn is next (no thundering herd). Termination is the part people miss: when next > MAX, each exiting thread wakes its successor, so the wakeups travel around the ring until every thread has left.

Java 
class RoundRobinPrinter {
  private final int n, max;
  private int next = 1;                       // guarded by lock
  private final ReentrantLock lock = new ReentrantLock();
  private final Condition[] turn;

  RoundRobinPrinter(int n, int max) {
    this.n = n; this.max = max;
    turn = new Condition[n];
    for (int i = 0; i < n; i++) turn[i] = lock.newCondition();
  }

  void run(int id) {
    lock.lock();
    try {
      while (true) {
        while (next <= max && (next - 1) % n != id) turn[id].await();
        if (next > max) {                     // done: pass the wakeup on
          turn[(id + 1) % n].signal();
          return;
        }
        System.out.println("T" + id + " -> " + next);
        next++;
        turn[(next - 1) % n].signal();        // wake only the next owner
      }
    } catch (InterruptedException e) {
      Thread.currentThread().interrupt();
    } finally {
      lock.unlock();
    }
  }
}
// for (int i = 0; i < n; i++) { int id = i; new Thread(() -> p.run(id)).start(); }
Go 
func RoundRobin(n, max int) {
  chans := make([]chan int, n)
  for i := range chans {
    chans[i] = make(chan int, 1) // buffer 1 so n == 1 can't self-deadlock
  }
  var wg sync.WaitGroup
  for i := 0; i < n; i++ {
    wg.Add(1)
    go func(id int) {
      defer wg.Done()
      next := chans[(id+1)%n]
      defer close(next) // each goroutine closes its successor exactly once
      for v := range chans[id] {
        if v > max {
          return
        }
        fmt.Printf("G%d -> %d\n", id, v)
        next <- v + 1
      }
    }(i)
  }
  chans[0] <- 1
  wg.Wait()
}

What to say in the interview: the while guards against spurious wakeups; per-thread Conditions make it O(1) wakeups per print instead of N; the close chain in Go is the channel version of “pass the wakeup on”.

Type B

Producer–consumer

Worked problem

Bounded blocking queue (LC 1188). Implement put (blocks when full), take (blocks when empty), poll(timeout), and size. It must be interruptible.

Show solution

One lock, two Conditions. Because producers only wait on notFull and consumers only on notEmpty, a single signal() always wakes the right kind of thread, so you don't need signalAll(). A circular array avoids allocating a node per element.

Java 
public final class BoundedBlockingQueue<E> {
  private final Object[] items;
  private int head, tail, count;              // guarded by lock
  private final ReentrantLock lock = new ReentrantLock();
  private final Condition notFull = lock.newCondition();
  private final Condition notEmpty = lock.newCondition();

  public BoundedBlockingQueue(int capacity) { items = new Object[capacity]; }

  public void put(E e) throws InterruptedException {
    lock.lockInterruptibly();
    try {
      while (count == items.length) notFull.await();
      items[tail] = e;
      tail = (tail + 1) % items.length;
      count++;
      notEmpty.signal();
    } finally { lock.unlock(); }
  }

  public E take() throws InterruptedException {
    lock.lockInterruptibly();
    try {
      while (count == 0) notEmpty.await();
      return dequeue();
    } finally { lock.unlock(); }
  }

  public E poll(long timeout, TimeUnit unit) throws InterruptedException {
    long nanos = unit.toNanos(timeout);
    lock.lockInterruptibly();
    try {
      while (count == 0) {
        if (nanos <= 0) return null;
        nanos = notEmpty.awaitNanos(nanos);   // returns time left
      }
      return dequeue();
    } finally { lock.unlock(); }
  }

  public int size() {
    lock.lock();
    try { return count; } finally { lock.unlock(); }
  }

  @SuppressWarnings("unchecked")
  private E dequeue() {
    E e = (E) items[head];
    items[head] = null;                       // let GC reclaim it
    head = (head + 1) % items.length;
    count--;
    notFull.signal();
    return e;
  }
}
Go 
// A buffered channel already is a bounded blocking queue.
// The interview value is adding cancellation and timeouts.
type Queue[T any] struct{ ch chan T }

func NewQueue[T any](n int) *Queue[T] { return &Queue[T]{ch: make(chan T, n)} }

func (q *Queue[T]) Put(ctx context.Context, v T) error {
  select {
  case q.ch <- v:
    return nil
  case <-ctx.Done():
    return ctx.Err()
  }
}

func (q *Queue[T]) Take(ctx context.Context) (T, error) {
  select {
  case v := <-q.ch:
    return v, nil
  case <-ctx.Done():
    var zero T
    return zero, ctx.Err()
  }
}

Follow-ups to expect: why size() needs the lock (visibility), how LinkedBlockingQueue uses two locks so put and take don't contend, and what happens to blocked producers on shutdown.

Type C

Rate and resource limiting

Worked problem

Per-client token bucket. allow(clientId) returns true if the client is under its limit: bursts up to capacity, refilling at ratePerSec. Thousands of clients, many threads, no background refill thread.

Show solution

Refill lazily: on each call, add elapsed × rate tokens (capped at capacity), then try to spend one. Each bucket has its own lock, so different clients never contend. computeIfAbsent creates each bucket exactly once.

Java 
public final class RateLimiter {
  private final ConcurrentHashMap<String, Bucket> buckets = new ConcurrentHashMap<>();
  private final long capacity;
  private final double ratePerNano;

  public RateLimiter(long capacity, double ratePerSec) {
    this.capacity = capacity;
    this.ratePerNano = ratePerSec / 1_000_000_000.0;
  }

  public boolean allow(String clientId) {
    return buckets.computeIfAbsent(clientId, k -> new Bucket()).tryAcquire();
  }

  private final class Bucket {
    private double tokens = capacity;         // guarded by this
    private long last = System.nanoTime();    // monotonic, not wall clock

    synchronized boolean tryAcquire() {
      long now = System.nanoTime();
      tokens = Math.min(capacity, tokens + (now - last) * ratePerNano);
      last = now;
      if (tokens >= 1) { tokens -= 1; return true; }
      return false;
    }
  }
}
Go 
type bucket struct {
  mu     sync.Mutex
  tokens float64
  last   time.Time
}

type Limiter struct {
  buckets  sync.Map // clientID -> *bucket
  capacity float64
  rate     float64 // tokens per second
}

func (l *Limiter) Allow(id string) bool {
  v, _ := l.buckets.LoadOrStore(id, &bucket{tokens: l.capacity, last: time.Now()})
  b := v.(*bucket)
  b.mu.Lock()
  defer b.mu.Unlock()
  now := time.Now() // carries a monotonic reading
  b.tokens = min(l.capacity, b.tokens+now.Sub(b.last).Seconds()*l.rate)
  b.last = now
  if b.tokens >= 1 {
    b.tokens--
    return true
  }
  return false
}

Talking points: nanoTime vs currentTimeMillis (clock jumps), evicting idle clients (a periodic sweep, or Caffeine with expireAfterAccess), a lock-free version with CAS on a packed long, and how this changes when the limit is shared across many servers (Redis + Lua script).

Type D

Build a primitive

Worked problem

Writer-preferring read-write lock. Many readers may hold it at once; a writer holds it alone. Once a writer is waiting, new readers must wait so writers are not starved.

Show solution

Three fields under one monitor: active readers, whether a writer is active, and how many writers are waiting. Readers wait while a writer is active or waiting. The subtle bug to avoid: if a waiting writer is interrupted, readers blocked on waitingWriters > 0 must be woken, or they wait forever.

Java 
public final class WriterPreferringRWLock {
  private int readers;            // all guarded by this
  private int waitingWriters;
  private boolean writing;

  public synchronized void lockRead() throws InterruptedException {
    while (writing || waitingWriters > 0) wait();
    readers++;
  }

  public synchronized void unlockRead() {
    if (readers <= 0) throw new IllegalMonitorStateException();
    if (--readers == 0) notifyAll();          // a writer may be waiting
  }

  public synchronized void lockWrite() throws InterruptedException {
    waitingWriters++;
    try {
      while (writing || readers > 0) wait();
    } catch (InterruptedException e) {
      waitingWriters--;
      notifyAll();                            // unblock readers we were holding back
      throw e;
    }
    waitingWriters--;
    writing = true;
  }

  public synchronized void unlockWrite() {
    if (!writing) throw new IllegalMonitorStateException();
    writing = false;
    notifyAll();
  }
}
Go 
type RWLock struct {
  mu             sync.Mutex
  cond           *sync.Cond
  readers        int
  waitingWriters int
  writing        bool
}

func NewRWLock() *RWLock {
  l := &RWLock{}
  l.cond = sync.NewCond(&l.mu)
  return l
}

func (l *RWLock) RLock() {
  l.mu.Lock()
  for l.writing || l.waitingWriters > 0 {
    l.cond.Wait()
  }
  l.readers++
  l.mu.Unlock()
}

func (l *RWLock) RUnlock() {
  l.mu.Lock()
  l.readers--
  if l.readers == 0 {
    l.cond.Broadcast()
  }
  l.mu.Unlock()
}

func (l *RWLock) Lock() {
  l.mu.Lock()
  l.waitingWriters++
  for l.writing || l.readers > 0 {
    l.cond.Wait()
  }
  l.waitingWriters--
  l.writing = true
  l.mu.Unlock()
}

func (l *RWLock) Unlock() {
  l.mu.Lock()
  l.writing = false
  l.cond.Broadcast()
  l.mu.Unlock()
}

The trade-off to state: this can now starve readers under a steady stream of writers. A fair alternative hands the lock over in phases (all waiting readers, then one writer). notifyAll is needed because readers and writers share one wait set.

Type E

Scheduling and time

Worked problem

Delayed task scheduler. schedule(task, delay) runs the task after the delay on a worker pool. Scheduling a task that is due earlier than everything else must still fire on time. No busy-waiting.

Show solution

One dispatcher thread sleeps on a Condition until the earliest job is due. awaitNanos can be woken early, so when a new job becomes the head of the heap, schedule signals the dispatcher to re-plan its sleep. User code runs on the worker pool, never on the dispatcher, so a slow task can't delay other tasks.

Java 
public final class DelayScheduler implements AutoCloseable {
  private record Job(long runAt, long seq, Runnable task) {}

  private final PriorityQueue<Job> heap = new PriorityQueue<>(
      Comparator.comparingLong(Job::runAt).thenComparingLong(Job::seq));
  private final ReentrantLock lock = new ReentrantLock();
  private final Condition changed = lock.newCondition();
  private final ExecutorService workers;
  private final Thread dispatcher;
  private long seq;                 // guarded by lock; keeps FIFO for equal times
  private boolean closed;           // guarded by lock

  public DelayScheduler(int nWorkers) {
    workers = Executors.newFixedThreadPool(nWorkers);
    dispatcher = new Thread(this::dispatch, "scheduler-dispatch");
    dispatcher.start();
  }

  public void schedule(Runnable task, long delay, TimeUnit unit) {
    lock.lock();
    try {
      if (closed) throw new RejectedExecutionException("closed");
      Job job = new Job(System.nanoTime() + unit.toNanos(delay), seq++, task);
      heap.add(job);
      if (heap.peek() == job) changed.signal(); // new earliest job
    } finally { lock.unlock(); }
  }

  private void dispatch() {
    lock.lock();
    try {
      while (!closed) {
        Job head = heap.peek();
        if (head == null) { changed.await(); continue; }
        long wait = head.runAt() - System.nanoTime();
        if (wait > 0) { changed.awaitNanos(wait); continue; }
        heap.poll();
        workers.execute(head.task());
      }
    } catch (InterruptedException e) {
      Thread.currentThread().interrupt();
    } finally { lock.unlock(); }
  }

  @Override public void close() {
    lock.lock();
    try { closed = true; changed.signal(); } finally { lock.unlock(); }
    workers.shutdown();
  }
}

  return h[i].at.Before(h[j].at)
}
func (h jobHeap) Swap(i, j int) { h[i], h[j] = h[j], h[i] }
func (h *jobHeap) Push(x any)   { *h = append(*h, x.(job)) }
func (h *jobHeap) Pop() any {
  old := *h
  j := old[len(old)-1]
  *h = old[:len(old)-1]
  return j
}

type Scheduler struct {
  add  chan job
  quit chan struct{}
}

func NewScheduler() *Scheduler {
  s := &Scheduler{add: make(chan job), quit: make(chan struct{})}
  go s.loop()
  return s
}

func (s *Scheduler) Schedule(fn func(), d time.Duration) {
  select {
  case s.add <- job{at: time.Now().Add(d), fn: fn}:
  case <-s.quit:
  }
}

func (s *Scheduler) Close() { close(s.quit) }

// One goroutine owns the heap, so no mutex is needed.
func (s *Scheduler) loop() {
  var h jobHeap
  var seq int64
  timer := time.NewTimer(time.Hour)
  for {
    if h.Len() > 0 {
      timer.Reset(time.Until(h[0].at)) // Go 1.23+: Reset is safe without draining
    }
    select {
    case j := <-s.add:
      j.seq = seq
      seq++
      heap.Push(&h, j)
    case <-timer.C:
      for h.Len() > 0 && !h[0].at.After(time.Now()) {
        go heap.Pop(&h).(job).fn() // hand off; never run user code here
      }
    case <-s.quit:
      timer.Stop()
      return
    }
  }
}

Follow-ups: cancel (return a handle with a cancelled flag, check it before running), fixed-rate vs fixed-delay repeats (compute next time from the scheduled time to avoid drift), and bounding the Go hand-off with a worker pool instead of go.

Type F

Parallel work and termination

Worked problem

Multithreaded web crawler (LC 1242). Starting from a URL, crawl every page on the same host using a pool of threads. getUrls(url) is a slow blocking call. Return every URL found. Don't sleep or poll to decide when you're done.

Show solution

The hard part is termination: the frontier can be empty while a worker is about to discover new links. Keep a counter of pending tasks. Increment it before submitting a child, and decrement it when a task finishes. Because the child's increment happens before the parent's decrement, the counter can only reach zero when there is truly no work left. Set.add returning true is the atomic “claim this URL”.

Java 
class Solution {
  private ExecutorService pool;
  private Set<String> seen;
  private AtomicInteger pending;
  private CountDownLatch done;
  private HtmlParser parser;
  private String host;

  public List<String> crawl(String startUrl, HtmlParser parser) {
    this.parser = parser;
    this.host = hostOf(startUrl);
    this.pool = Executors.newFixedThreadPool(8);
    this.seen = ConcurrentHashMap.newKeySet();
    this.pending = new AtomicInteger();
    this.done = new CountDownLatch(1);

    seen.add(startUrl);
    submit(startUrl);
    try {
      done.await();
    } catch (InterruptedException e) {
      Thread.currentThread().interrupt();
    } finally {
      pool.shutdownNow();
    }
    return new ArrayList<>(seen);
  }

  private void submit(String url) {
    pending.incrementAndGet();                // before the parent finishes
    pool.execute(() -> {
      try {
        for (String next : parser.getUrls(url)) {
          if (hostOf(next).equals(host) && seen.add(next)) submit(next);
        }
      } finally {
        if (pending.decrementAndGet() == 0) done.countDown();
      }
    });
  }

  private static String hostOf(String url) {
    return url.split("/")[2];                 // "http://host/path" -> "host"
  }
}
Go 
func Crawl(start string, getURLs func(string) []string, limit int) []string {
  host := hostOf(start)
  var mu sync.Mutex
  seen := map[string]bool{start: true}
  sem := make(chan struct{}, limit) // at most `limit` fetches at once
  var wg sync.WaitGroup

  var visit func(string)
  visit = func(u string) {
    defer wg.Done()
    sem <- struct{}{}
    urls := getURLs(u)
    <-sem // release before spawning, so children can't deadlock on the semaphore
    for _, next := range urls {
      if hostOf(next) != host {
        continue
      }
      mu.Lock()
      isNew := !seen[next]
      seen[next] = true
      mu.Unlock()
      if isNew {
        wg.Add(1) // Add before go, same rule as the Java increment
        go visit(next)
      }
    }
  }

  wg.Add(1)
  go visit(start)
  wg.Wait()

  out := make([]string, 0, len(seen))
  for u := range seen {
    out = append(out, u)
  }
  return out
}

func hostOf(u string) string { return strings.Split(u, "/")[2] }

Type G

Concurrent caches and maps

Worked problem

Load-once cache. get(key) returns a cached value or loads it with an expensive loader. If 100 threads miss on the same key at the same moment, the loader must run exactly once and all 100 get its result. Loads for different keys must not block each other.

Show solution

Cache the future, not the value. The first thread to putIfAbsent its future owns the load. Everyone else finds that future and waits on it. On failure, remove the future so the next caller can retry. This is the Memoizer from Java Concurrency in Practice §5.6.

Java 
public final class LoadingCache<K, V> {
  private final ConcurrentHashMap<K, CompletableFuture<V>> map = new ConcurrentHashMap<>();
  private final Function<K, V> loader;

  public LoadingCache(Function<K, V> loader) { this.loader = loader; }

  public V get(K key) throws InterruptedException, ExecutionException {
    CompletableFuture<V> f = map.get(key);
    if (f == null) {
      CompletableFuture<V> mine = new CompletableFuture<>();
      f = map.putIfAbsent(key, mine);
      if (f == null) {                        // we won: run the load
        f = mine;
        try {
          mine.complete(loader.apply(key));
        } catch (Throwable t) {
          map.remove(key, mine);              // allow a retry
          mine.completeExceptionally(t);
        }
      }
    }
    return f.get();
  }
}
Go 
type call[V any] struct {
  done chan struct{} // closed when val/err are set
  val  V
  err  error
}

type LoadingCache[K comparable, V any] struct {
  mu     sync.Mutex
  m      map[K]*call[V]
  loader func(K) (V, error)
}

func NewLoadingCache[K comparable, V any](loader func(K) (V, error)) *LoadingCache[K, V] {
  return &LoadingCache[K, V]{m: make(map[K]*call[V]), loader: loader}
}

func (c *LoadingCache[K, V]) Get(k K) (V, error) {
  c.mu.Lock()
  if cl, ok := c.m[k]; ok {
    c.mu.Unlock()
    <-cl.done
    return cl.val, cl.err
  }
  cl := &call[V]{done: make(chan struct{})}
  c.m[k] = cl
  c.mu.Unlock() // never hold the lock while loading

  cl.val, cl.err = c.loader(k)
  if cl.err != nil {
    c.mu.Lock()
    delete(c.m, k)
    c.mu.Unlock()
  }
  close(cl.done) // publishes val/err to waiters (happens-before)
  return cl.val, cl.err
}

Why not map.computeIfAbsent(key, loader)? It works, but it holds a lock on the hash bin while the loader runs. That blocks other keys in the same bin, and a loader that touches the same map can deadlock or throw. Add TTL and size bounds as follow-ups.

Type H

Spot the bug

Interviewers paste a snippet and ask what's wrong. Find the bug before you open each answer.

1 · Java 
ConcurrentHashMap<String, Integer> counts = new ConcurrentHashMap<>();
void record(String k) {
  Integer c = counts.get(k);
  counts.put(k, c == null ? 1 : c + 1);
}
Show answer

Check-then-act. Each call is thread-safe on its own, but the get-then-put pair is not atomic, so concurrent increments are lost. Fix: counts.merge(k, 1, Integer::sum). Under heavy contention, use ConcurrentHashMap<String, LongAdder> with computeIfAbsent(k, x -> new LongAdder()).increment().

2 · Java 
private Integer count = 0;
void inc() {
  synchronized (count) { count++; }
}
Show answer

count++ on a boxed Integer assigns a new object, so threads lock different monitors and there is no mutual exclusion. Small Integers are also cached and shared JVM-wide, so unrelated code can lock the same object. Always lock on a private final Object.

3 · Java 
synchronized void await() throws InterruptedException {
  if (!ready) wait();
  use(data);
}
Show answer

if instead of while. wait() can return spuriously, or another thread can change the state between the notify and this thread getting the lock back. Always re-check the condition in a loop.

4 · Java 
ExecutorService pool = Executors.newFixedThreadPool(4);
Future<Report> build(Order o) {
  return pool.submit(() -> {
    Future<Price> p = pool.submit(() -> price(o));
    Future<Stock> s = pool.submit(() -> stock(o));
    return new Report(p.get(), s.get());
  });
}
Show answer

Pool-induced deadlock. Under load, 4 outer tasks occupy all 4 workers and block on get(); the subtasks sit in the queue with no one to run them. Fix: a separate pool for subtasks, CompletableFuture composition with no blocking get() inside a worker, or ForkJoin, which lets a joining thread run other tasks.

5 · Go 
var wg sync.WaitGroup
for _, u := range urls {
  go func() {
    wg.Add(1)
    defer wg.Done()
    fetch(u)
  }()
}
wg.Wait()
Show answer

wg.Add(1) is inside the goroutine, so Wait() can run before any goroutine has called Add and return immediately. Call wg.Add(1) before the go statement (or wg.Add(len(urls)) once). Before Go 1.22 the loop variable u was also shared across iterations.

6 · Go 
func fetchWithTimeout() (string, error) {
  ch := make(chan string)
  go func() { ch <- slowCall() }()
  select {
  case v := <-ch:
    return v, nil
  case <-time.After(time.Second):
    return "", ErrTimeout
  }
}
Show answer

Goroutine leak. After a timeout nobody reads from ch, so the goroutine blocks on its send forever. Under steady timeouts this leaks thousands of goroutines. Fix: make(chan string, 1) so the send always completes, and ideally pass a context into slowCall so it stops working too.

Practice (production debugging)
  1. MED
    p99 latency jumped and a thread dump shows 180 of 200 threads BLOCKED on the same monitor. Walk through what you do next.
    Hint

    Find the owner thread in the dump and what it is doing (often I/O under a lock). Fixes: shrink the critical section, move I/O outside it, or stripe the lock.

  2. MED
    A Go service's memory grows slowly and never drops. The goroutine count in pprof grows with traffic.
    Hint

    /debug/pprof/goroutine?debug=2, group by stack. Look for goroutines stuck on channel sends or receives with no context.

  3. HARD
    A job runs fine with 4 threads and hangs with 16. There are no exceptions and CPU usage is 0%.
    Hint

    0% CPU with a hang means a deadlock or starvation, not a hot loop. Check jstack for “Found one Java-level deadlock”, then check for a bounded resource (like a DB pool of 10) that 16 threads each need two of.
