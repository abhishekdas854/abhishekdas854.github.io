How to practise

  • Time-box it. 25 minutes for easy, 40 for medium, 60 for hard, including tests. Speak your design out loud before you write code.
  • Write the stress test first. Many threads, a start gate, many iterations, and an invariant check. Then make sure the test fails on a deliberately broken version.
  • Put the code in your prep repo under java/src/main/java/prep/practice/pNN/ or go/practice/pNN/ and add a few lines to NOTES.md.
  • Get it reviewed: open Claude Code in the repo and ask Review practice problem 13. It's scored with the same rubric as the course.
Group 1

Classic synchronisation puzzles

P01

Ordered printing

EASYordering

Three threads are started in random order. One calls first(), one second(), one third(). The output must always be “first second third”.

class Ordered {
  void first(Runnable print)  throws InterruptedException;
  void second(Runnable print) throws InterruptedException;
  void third(Runnable print)  throws InterruptedException;
}
  • Solve it three ways: CountDownLatch, Semaphore, and a monitor with an int stage.
  • No busy-waiting.
Hint 1

You need two “gates”: after first, after second.

Hint 2

With a monitor: while (stage != 2) wait(); then print, increment, notifyAll().

Reviewer checks: correct under 1,000 random start orders; say which version you'd ship and why.

P02

Foo and bar, n times

EASYordering

Two threads share one object. One loops calling foo() n times, the other bar() n times. Output must be foobarfoobar… with exactly n pairs.

  • Solve with two semaphores, then with ReentrantLock and one Condition, then in Go with two unbuffered channels.
Hint 1

Semaphores fooTurn = 1, barTurn = 0. Each side acquires its own and releases the other's.

Reviewer checks: works with n = 0 and n = 1; no thread left blocked at the end.

P03

Zero, even, odd

MEDordering

Three threads: one prints only 0, one only even numbers, one only odd numbers. Together they print 0 1 0 2 0 3 … 0 n.

Hint 1

The zero thread is the conductor: it prints 0 and then decides who goes next.

Hint 2

Three semaphores (zero = 1, odd = 0, even = 0). The odd and even threads release zero when done.

Reviewer checks: n odd and n even both terminate; no thread waits forever for a turn that never comes.

P04

Multithreaded FizzBuzz

MEDordering

Four threads print FizzBuzz from 1 to n: one prints “Fizz”, one “Buzz”, one “FizzBuzz”, one plain numbers. The sequence must be the normal FizzBuzz order.

Hint 1

Share one counter under a monitor. Each thread waits until the counter is a number it owns, or is past n.

Hint 2

Use notifyAll: the next owner can be any of the three other threads.

Reviewer checks: all four threads exit, including the ones whose last number came earlier.

P05

Build a molecule

MEDgrouping

Hydrogen and oxygen threads arrive at random. They must leave in groups of exactly two H and one O, and a group's three threads must all “bond” before any thread from the next group does.

Hint 1

Admission: Semaphore h = 2, Semaphore o = 1.

Hint 2

A CyclicBarrier(3) whose barrier action releases 2 H permits and 1 O permit for the next group.

Reviewer checks: with 2,000 H and 1,000 O threads, every consecutive block of three printed atoms is exactly H, H, O in some order.

P06

Dining philosophers

MEDdeadlock

Five philosophers, five forks, each needs both neighbouring forks to eat. Implement wantsToEat(id, pickLeft, pickRight, eat, putLeft, putRight) with no deadlock.

  • Give two different solutions and explain which deadlock condition each one breaks.
Hint 1

Resource ordering: always pick up the lower-numbered fork first.

Hint 2

Or limit the table: a Semaphore(4) so at most four philosophers try at once.

Reviewer checks: 100,000 meals with no deadlock; can any philosopher starve in your solution?

P07

Barber shop

MEDproducer–consumer

A shop has one barber and N waiting chairs. A customer who finds all chairs taken leaves. If the barber is asleep, an arriving customer wakes them. Each haircut is for exactly one customer, and the customer can't leave until their cut is done.

Hint 1

State under a lock: waiting count. Semaphores: customers waiting, barber ready, haircut done.

Hint 2

Extend to K barbers. What changes, and what doesn't?

Reviewer checks: served + turned away = arrivals; never more than N waiting.

P08

Shared bathroom

HARDfairness

One bathroom may be used by at most 3 people at a time, and only by members of one of two groups at a time (group A or group B). Implement useA(Runnable) and useB(Runnable). Neither group may starve the other.

Hint 1

State: current group, number inside, number of each group waiting. Plus a Semaphore(3) for capacity.

Hint 2

To avoid starvation, stop admitting the current group once the other group has someone waiting (like a writer-preferring RW lock).

Reviewer checks: never mixed groups, never more than 3; a steady stream of A cannot block B forever.

P09

Ride-share seating

HARDgrouping

Riders from two groups (say, fans of two rival teams) arrive at random and are seated four to a car. Allowed cars: four of one group, or two and two. Three of one and one of the other is never allowed. Exactly one rider of each car calls drive(), after all four have called seated().

Hint 1

A lock guards the counts of each group waiting. The arriving rider who completes a valid four becomes the driver and releases the other three.

Hint 2

One semaphore per group to release chosen riders, and a CyclicBarrier(4) so the driver waits until everyone is seated.

Reviewer checks: every car is a valid mix; exactly one drive() per car; no rider seated twice.

P10

Lazy singleton

EASYmemory model

Create a singleton that's created on first use, created exactly once under any number of concurrent callers, and cheap to access afterwards.

  • Write the broken version, double-checked locking with volatile, the holder idiom, and the enum version. In Go, use sync.OnceValue.
Hint 1

Count constructor calls with an AtomicInteger and release 64 threads through a latch at once.

Reviewer checks: explain exactly why volatile is needed; how reflection or serialization could still create a second instance.

Group 2

Build the primitive yourself

P11

Counting semaphore

MEDmonitor
class MySemaphore {
  MySemaphore(int permits);
  void acquire() throws InterruptedException;
  boolean tryAcquire(long timeout, TimeUnit unit) throws InterruptedException;
  void release();
}
  • Built only from synchronized/wait/notify. Then add acquire(n) and argue whether notify is still safe.
Hint 1

With acquire(n), a single notify can wake a thread needing 5 permits when only 1 is free, and the signal is lost. Use notifyAll.

Reviewer checks: never more than N holders; timeouts accurate to about 10 ms; interrupt handled.

P12

Reusable barrier

MEDmonitor

Implement await() for N parties that can be used round after round. A fast thread that loops back must not slip through the next round early.

Hint 1

Keep a generation number. Waiters remember the generation they arrived in and wait until it changes.

Hint 2

The last arriver resets the count, bumps the generation and calls notifyAll.

Reviewer checks: 10,000 rounds with 8 threads; a per-round counter proves nobody ran ahead.

P13

Closable blocking queue

MEDproducer–consumer

Extend a bounded blocking queue with close(). After close, put throws, blocked producers wake and throw, and take drains the remaining items and then returns an end-of-stream marker (empty Optional) to every consumer, including ones already blocked.

Hint 1

A closed flag under the same lock, and signalAll on both conditions in close().

Hint 2

Compare with Go, where this is just close(ch) plus v, ok := <-ch.

Reviewer checks: nothing lost, nothing delivered after end-of-stream, no consumer left blocked.

P14

Async to sync

MEDbridging

A library offers void compute(Input in, Consumer<Result> callback), which returns immediately and later calls the callback on a thread of its own. Write Result computeSync(Input in, long timeoutMs) that blocks until the callback fires or the timeout passes.

  • The callback might fire before compute even returns, and might (buggily) fire twice.
Hint 1

A CompletableFuture or a CountDownLatch(1) plus a volatile result field; both remember a signal that arrives early.

Hint 2

On timeout, what happens if the callback fires later? Make sure that's harmless.

Reviewer checks: no missed signal when the callback fires synchronously; the second callback is ignored.

P15

Deferred callback executor

MEDscheduling

Threads register callbacks, each with a delay in milliseconds. A single executor thread runs each callback once its time comes, in time order. Registering a callback that's due sooner than everything else must wake the executor.

Hint 1

A min-heap by due time and one Condition. The executor sleeps with awaitNanos(head.due − now).

Hint 2

Always recompute the wait after waking: it may be a new earlier head, a spurious wakeup, or the real deadline.

Reviewer checks: each callback runs within 10 ms of its time; zero CPU while idle.

P16

Token bucket with a refill thread

MEDrate limiting

Build a blocking token bucket (getToken() waits until a token is available) in two versions: a daemon thread adds one token per interval, and a lazy version with no thread that computes tokens from elapsed time. Provide the threaded version through a factory method.

Hint 1

Why a factory? Starting a thread in a constructor lets this escape before construction finishes.

Hint 2

In the lazy version, a waiter can compute how long until the next token and sleep exactly that long, instead of polling.

Reviewer checks: over 5 seconds at 10 tokens/s, 50 ± 1 tokens granted to 20 competing threads; compare the two designs.

P17

Upgradeable read-write lock

HARDmonitor

A read-write lock with a third mode, upgradeableRead. Only one thread can hold it at a time, it coexists with plain readers, and it can be upgraded to a write lock without deadlock.

Hint 1

Upgrade deadlock happens when two readers both try to upgrade. Allowing only one upgradeable holder removes that cycle.

Reviewer checks: an interleaving argument for why upgrade can't deadlock; tests for each mode pair.

P18

Multithreaded merge sort

MEDparallelism

Sort a 50-million-element int array in parallel. Version 1 starts a new thread for each half (and shows why that's a bad idea). Version 2 uses ForkJoinPool with a sequential cutoff. In Go, bound the goroutines with a depth limit.

Hint 1

Share one scratch buffer across the whole sort instead of allocating one per merge.

Hint 2

Plot time against cutoff size (1K, 10K, 100K) and core count. Where does Amdahl show up?

Reviewer checks: matches Arrays.sort; a speedup table; explain why the merge step limits scaling.

Group 3

System components

P19

Hot-reloadable config

EASYpublication

Many request threads read a config object on every request. A background thread reloads it from disk every 30 seconds. Readers must never see a half-updated config and must never block.

Hint 1

Immutable config object plus an AtomicReference (or a volatile field), swapped in one write. This is the read-copy-update (RCU) pattern.

Reviewer checks: readers take no lock; a reader that reads two fields sees them from the same version.

P20

Unique ID generator

MEDatomics

Build a Snowflake-style 64-bit ID generator: 41 bits of milliseconds, 10 bits of machine ID, 12 bits of sequence. IDs must be unique and increasing, even with 64 threads calling at once and even if the clock steps backwards.

Hint 1

Pack (lastMillis, sequence) into one AtomicLong and advance it with a CAS loop.

Hint 2

If the sequence overflows within a millisecond, move to the next millisecond. If the clock goes backwards, keep using the last timestamp.

Reviewer checks: 10 million IDs from 64 threads with no duplicates; simulated clock-skew test.

P21

Circuit breaker

MEDstate machine

call(Supplier<T>) with CLOSED, OPEN and HALF_OPEN states. After 5 failures in a row it opens and fails fast for 10 seconds. Then exactly one trial call is let through; success closes the breaker, failure reopens it.

Hint 1

Use an AtomicReference to an immutable state record, updated by CAS, so exactly one thread wins the OPEN → HALF_OPEN transition.

Reviewer checks: with 100 threads arriving as the timeout ends, exactly one trial call goes through.

P22

Object pool with validation

MEDresource limit

A generic pool: borrow(timeout), giveBack(obj), invalidate(obj). It creates objects lazily up to max, validates an object before handing it out, replaces broken ones, and closes idle objects after 60 seconds.

Hint 1

A Semaphore(max) for capacity, and a concurrent deque of idle objects. Keep the semaphore and the deque consistent when creation throws.

Reviewer checks: never more than max objects alive; no permit leak when the factory throws; double give-back detected.

P23

Merge K sorted streams

MEDproducer–consumer

K producer threads each emit a sorted stream of timestamps at their own pace. One consumer must output the merged, globally sorted stream as soon as it's safe to do so.

Hint 1

You can only emit the smallest item once every producer has either given you its next item or finished. One small queue per producer plus a heap.

Hint 2

In Go this is a select-free loop: block on each producer's channel only when its head is empty.

Reviewer checks: output sorted and complete; a slow producer delays output but doesn't cause errors.

P24

Parallel downloader

MEDGo first

Download 500 URLs with at most 8 in flight at once and at most 2 per host. Report progress (done, failed, bytes) every second. Ctrl-C cancels everything cleanly and prints a summary.

Hint 1

A global semaphore channel plus a map of per-host semaphores created lazily under a mutex.

Hint 2

signal.NotifyContext for Ctrl-C; atomic counters read by a ticker goroutine.

Reviewer checks: limits respected (instrument and assert); no goroutine leak after cancel; Java version with virtual threads for comparison.

P25

Keyed (striped) executor

HARDordering

execute(key, task): tasks with the same key run one at a time in submission order; tasks with different keys run in parallel on a shared pool. Keys are unbounded (user IDs), so per-key state must be cleaned up when idle.

Hint 1

Per key, keep a tail CompletableFuture and chain the new task onto it with thenRunAsync(task, pool).

Hint 2

Remove the key's entry when its tail completes, but only if it's still the tail (map.remove(key, tail)).

Reviewer checks: per-key order holds across 1M tasks; the map is empty after everything is done; different keys really run in parallel.

P26

Request batcher

HARDbatching

Callers call CompletableFuture<V> load(K key) one key at a time. The batcher collects keys and calls the backend's Map<K,V> loadAll(Set<K>) once 100 keys are waiting or 10 ms have passed since the first one, whichever comes first. Duplicate keys in a batch share one lookup.

Hint 1

Under a lock, keep a map from key to a list of futures, and a flag for whether a flush is scheduled.

Hint 2

Swap the pending map out under the lock, then call the backend outside it. Complete missing keys exceptionally so no caller waits forever.

Reviewer checks: batch sizes ≤ 100; latency ≤ 10 ms plus the backend time; backend failure fails the whole batch cleanly.

P27

Bank with consistent audits

HARDconsistency

10,000 accounts, many threads doing random transfers. An auditor thread periodically sums all balances, and the sum must always equal the starting total. Transfers must not stop while the audit runs for long.

Hint 1

Naive approach: per-account locks in id order, plus a global RW lock where transfers take the read side and the audit takes the write side. What does that cost?

Hint 2

Better: versioned balances or a transaction log, so the audit reads a snapshot at a version without stopping writers.

Reviewer checks: every audit equals the total; transfer throughput during an audit; no deadlock in 1M transfers.

P28

Transactional key-value store

HARDisolation

begin(), get, put, commit(), rollback(), with each transaction bound to its caller. Other transactions never see uncommitted writes. Commit fails if another transaction committed a write to a key this one read (optimistic concurrency).

Hint 1

Each transaction keeps a read set with versions and a private write buffer.

Hint 2

Commit: under a short global lock (or per-key locks taken in sorted order), check that the read versions are unchanged, then apply the writes and bump versions.

Reviewer checks: a lost-update test (two increments of the same key) always ends with either both applied or one failing.

P29

Lease lock with fencing tokens

HARDdistributed

An in-memory lock service: acquire(clientId, leaseMs) returns a monotonically increasing token; leases expire; renew extends a lease. A storage class accepts write(token, data) only when the token is at least the highest seen. Simulate a client that pauses past its lease and then tries to write.

Hint 1

Expiry is checked on access (no timer thread needed), using a clock you can control in tests.

Reviewer checks: the paused client's write is rejected; explain what goes wrong without fencing.

P30

Deadline-aware task queue

HARDscheduling

A worker pool that runs tasks in order of earliest deadline. Tasks already past their deadline are dropped and their futures fail with a timeout. submit rejects a task if the queue's estimated wait (using a moving average of task duration) would already miss its deadline.

Hint 1

A PriorityBlockingQueue ordered by deadline, with workers checking the deadline on take.

Hint 2

The estimate is roughly queue position × average duration ÷ workers. Keep the average in an atomic, updated after each task.

Reviewer checks: no expired task is ever run; admission control keeps the miss rate low under 2× overload.
