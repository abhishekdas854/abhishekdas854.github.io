Section 1

Foundations

What is the difference between a program, a process and a thread?
Model answer

A program is code on disk. A process is a running instance of it with its own address space, file descriptors and at least one thread; processes are isolated, so sharing needs IPC. A thread is a unit of execution inside a process: it has its own stack, registers and program counter, but shares the heap and globals with the other threads of that process. Shared memory is what makes threads cheap to communicate through and what makes them dangerous.

Concurrency vs parallelism?
Model answer

Concurrency is structuring a program as independently progressing tasks whose lifetimes overlap; it works even on one core through interleaving. Parallelism is tasks literally executing at the same instant on multiple cores. Concurrency is about dealing with many things; parallelism is about doing many things. A web server handling 10,000 idle connections is highly concurrent and barely parallel.

Cooperative vs preemptive multitasking. Where do Java virtual threads and goroutines fit?
Model answer

In cooperative multitasking a task runs until it voluntarily yields, so one misbehaving task can starve the rest. In preemptive multitasking the scheduler interrupts tasks on a timer, which is what OS threads get. Java virtual threads are unmounted from their carrier only at blocking points (I/O, locks, sleep), so a tight CPU loop keeps its carrier busy. Goroutines were mostly cooperative until Go 1.14 added asynchronous preemption via signals, so a tight loop can now be preempted.

Synchronous vs asynchronous execution?
Model answer

A synchronous call blocks the caller until the result is ready. An asynchronous call returns immediately with a handle (a Future, a callback registration, a channel) and the result arrives later. Async frees the caller's thread but spreads control flow across callbacks; structured concurrency and virtual threads try to recover synchronous-looking code without the thread cost.

I/O-bound vs CPU-bound work: how does it change your thread count?
Model answer

CPU-bound threads are always busy, so more threads than cores only adds context switches: use about Ncpu (+1 to cover the occasional page fault). I/O-bound threads spend most of their time waiting, so you need more of them to keep the CPU busy: Ncpu × (1 + wait/compute). In practice the limit is often a downstream resource (DB connections, remote rate limits), so size against that too.

Throughput vs latency. Can adding threads make one better and the other worse?
Model answer

Throughput is work completed per unit time; latency is how long one piece of work takes. Yes: more threads can raise throughput while raising latency (more queueing and contention per request), and batching raises throughput by making individual items wait. Little's Law ties them together: concurrency = throughput × latency.

State Amdahl's Law. If 10% of a job is serial, what is the maximum speedup?
Model answer

speedup(n) = 1 / (s + (1 − s)/n), where s is the serial fraction and n the number of processors. With s = 0.1 the limit as n grows is 1/0.1 = 10×; with 16 cores you get about 6.4×. The practical lesson: shrinking the serial part (lock-held sections, single-threaded merge steps) matters more than adding cores. Gustafson's Law is the counterpoint: with more cores you usually grow the problem size, not just shrink the time.

What does Moore's Law have to do with concurrency?
Model answer

Transistor counts kept doubling, but around 2005 clock speeds stopped rising because of power and heat limits. Chip makers spent the extra transistors on more cores instead. Single-threaded code stopped getting faster for free, so exploiting parallelism became the programmer's job.

Define critical section, race condition and data race. Are the last two the same thing?
Model answer

A critical section is code that accesses shared state and must not be run by two threads at once. A race condition is a bug where correctness depends on timing, like check-then-act (if (!map.containsKey(k)) map.put(k, v)) or read-modify-write (count++). A data race is a memory-model term: two unsynchronised accesses to the same variable, at least one a write. They differ: you can have a race condition with no data race (each call is synchronised but the sequence isn't atomic), and a benign-looking data race without a logical race.

What are the four conditions for deadlock, and how do you break each?
Model answer
  • Mutual exclusion: resources can't be shared. Break it with lock-free structures or immutable data.
  • Hold and wait: a thread holds one resource while waiting for another. Break it by acquiring everything at once, or releasing before waiting.
  • No preemption: a resource can't be taken away. Break it with tryLock(timeout) and back off.
  • Circular wait: a cycle in the wait-for graph. Break it with a global lock order (e.g. by account id). This is the fix interviewers expect.
Deadlock vs livelock vs starvation, with an example of each.
Model answer

Deadlock: threads block forever waiting on each other (two transfers locking accounts in opposite order). Livelock: threads keep running but make no progress, e.g. two threads that both tryLock, fail, back off and retry in lockstep; fix with randomised backoff. Starvation: one thread never gets a turn, e.g. a writer that never acquires a read-preferring RW lock under constant reads; fix with fairness or writer preference.

What is a reentrant lock, and what would happen without reentrancy?
Model answer

A reentrant lock can be acquired again by the thread that already holds it; it keeps a hold count and is released when the count drops to zero. Without reentrancy, a synchronized method calling another synchronized method on the same object (or an overriding method calling super) would deadlock on itself. Both synchronized and ReentrantLock are reentrant; Semaphore is not.

Section 2

Synchronisation theory

Mutex vs semaphore?
Model answer

A mutex gives exclusive access and has an owner: only the thread that locked it may unlock it. A semaphore is a counter of permits with no owner: any thread can release, which makes it a signalling tool as well as a limit on concurrent access (e.g. at most 10 DB connections). A binary semaphore looks like a mutex but lacks ownership, so it can't be reentrant and can't detect an unlock by the wrong thread.

What is a monitor? How does it relate to a mutex?
Model answer

A monitor is a mutex plus one or more condition variables, bound to the data they protect. The mutex gives mutual exclusion; the condition variables let a thread wait for a state (“queue not empty”) while releasing the mutex atomically, and be woken when another thread changes it. In Java every object is a monitor: synchronized is the mutex and wait/notify the single condition variable.

Hoare vs Mesa monitors. Which does Java use, and what does it force you to write?
Model answer

In a Hoare monitor the signaller hands the monitor directly to the woken thread, so the condition is guaranteed true when it resumes. In a Mesa monitor, signalling only moves the waiter back to compete for the lock; by the time it runs, another thread may have changed the state. Java (and pthreads, and Go's sync.Cond) are Mesa, so you must re-check the condition in a loop: while (!cond) wait();. Mesa is cheaper and also tolerates spurious wakeups.

Semaphore vs monitor: when would you pick each?
Model answer

Use a semaphore when the state is naturally a count (permits, slots, items) or when one thread signals another with no shared data. Use a monitor when the waiting condition is an arbitrary predicate over shared state (“no writer active and no writer waiting”). Monitors are generally easier to reason about because the state and the lock live together; semaphores are easy to misuse with a forgotten or doubled release.

What is a missed signal, and how do you prevent it?
Model answer

A notify sent when no thread is waiting is lost: condition variables have no memory. If the signaller runs first, the waiter then calls wait() and sleeps forever. The fix is to always wait on a state predicate guarded by the lock (while (!ready) wait();), so a thread that arrives late sees the state change and never waits. A semaphore also works, because its permit count remembers the signal.

What is a spurious wakeup and why does it exist?
Model answer

A thread returns from wait() or await() without having been signalled. The spec allows it because some OS primitives (e.g. futex-based implementations handling signals) can't cheaply avoid it, and allowing it makes the implementation faster. The while loop around every wait handles it at no extra cost.

Section 3

Java primitives

What does synchronized guarantee? What is the difference between a synchronized instance method and a synchronized static method?
Model answer

Mutual exclusion on one monitor and visibility: everything a thread wrote before releasing the monitor is visible to the next thread that acquires it. An instance method locks this; a static method locks the Class object. They are different monitors, so a static and an instance synchronized method can run at the same time. Prefer locking on a private final Object so outside code can't take your lock.

Rules for wait, notify and notifyAll. When is notify safe?
Model answer
  • You must hold the object's monitor, or you get IllegalMonitorStateException.
  • wait() releases the monitor atomically and reacquires it before returning.
  • Always wait in a while loop over the predicate.
  • notify() wakes one arbitrary waiter. It's only safe when all waiters wait for the same condition and any one of them can make progress. If producers and consumers share one wait set, notify can wake the wrong kind and the signal is lost, so use notifyAll, or two Conditions.
How does thread interruption work, and what should you do when you catch InterruptedException?
Model answer

Interruption is cooperative: t.interrupt() sets a flag. Blocking methods (sleep, wait, join, BlockingQueue.take, lockInterruptibly) notice it, clear the flag and throw InterruptedException. Code that isn't blocking must poll Thread.currentThread().isInterrupted(). When you catch it, either rethrow, or restore the flag with Thread.currentThread().interrupt() so callers up the stack still see it. Never swallow it. Note Thread.interrupted() clears the flag; isInterrupted() doesn't. Waiting to enter a synchronized block can't be interrupted.

What does volatile guarantee, and when is it enough on its own?
Model answer

Visibility (a read sees the latest write) and ordering (a volatile write happens-before every later read of that variable, so writes made before it are visible too). It does not make compound actions atomic, so volatile int count; count++ still loses updates. It's enough when writes don't depend on the current value and the variable isn't part of an invariant with other variables: stop flags, a published immutable config reference, the instance field in double-checked locking.

ReentrantLock vs synchronized: what does the explicit lock add?
Model answer
  • tryLock() and tryLock(timeout) for deadlock avoidance.
  • lockInterruptibly().
  • Optional fairness (FIFO hand-off, lower throughput).
  • Multiple Conditions per lock (e.g. notFull and notEmpty).
  • Locking and unlocking in different scopes, e.g. hand-over-hand locking in a linked list.

The cost: you must unlock in finally yourself. Use synchronized by default for simple cases; it's also no longer a pinning problem for virtual threads from JDK 24.

How does AbstractQueuedSynchronizer (AQS) work?
Model answer

AQS is the base of ReentrantLock, Semaphore, CountDownLatch and ReentrantReadWriteLock. It holds one volatile int state updated by CAS and a FIFO queue of waiting threads (a CLH-queue variant). Subclasses define what acquiring and releasing mean by overriding tryAcquire/tryRelease (exclusive) or tryAcquireShared/tryReleaseShared (shared). AQS handles queuing, parking with LockSupport.park, waking successors, timeouts and interrupts. For a lock, state is the hold count; for a semaphore, the permits; for a latch, the remaining count.

Can you upgrade a read lock to a write lock in ReentrantReadWriteLock? Downgrade?
Model answer

Upgrade: no. Two readers trying to upgrade would each wait for the other to release its read lock, a guaranteed deadlock, so the thread just blocks forever. Downgrade: yes. Acquire the read lock while still holding the write lock, then release the write lock. StampedLock offers tryConvertToWriteLock, which fails instead of deadlocking.

What is StampedLock's optimistic read, and when is it worth it?
Model answer

tryOptimisticRead() returns a stamp without locking. You read the fields into locals, then call validate(stamp): if no write happened, the read was consistent; otherwise fall back to a real read lock. It's worth it for very read-heavy, short reads of a few fields (a point's x and y), because readers write nothing to shared memory. It isn't reentrant and has no Conditions.

Fair vs unfair locks: why is unfair the default?
Model answer

An unfair lock lets a newly arriving thread grab the lock ahead of queued ones (“barging”). That avoids waking a parked thread and waiting for it to be scheduled while the lock sits idle, so throughput is much higher. Fair locks guarantee FIFO order and prevent starvation, at a large throughput cost. Use fair only when you have observed starvation.

Why is double-checked locking broken without volatile? Give two better alternatives.
Model answer

instance = new Singleton() is allocation, construction and assignment. Without volatile, the assignment can become visible to another thread before the constructor's writes, so the unlocked first check sees a non-null reference to a half-built object. volatile adds the missing happens-before edge. Better alternatives: the holder idiom (a nested static class whose initialiser the JVM runs lazily and thread-safely) or an enum singleton.

Section 4

Java Memory Model

Why can instructions be reordered, and show a program whose outcome surprises people.
Model answer

Compilers, the JIT and CPUs reorder independent operations for speed (store buffers, out-of-order execution, register caching). Each thread still sees its own program order, but other threads may not.

int x = 0, y = 0;
// Thread 1: x = 1; r1 = y;
// Thread 2: y = 1; r2 = x;

Both r1 == 0 and r2 == 0 is possible, even though it is impossible under any interleaving of the four statements. Making x and y volatile forbids it.

List the main happens-before rules.
Model answer
  • Program order: each action in a thread happens-before later actions in that thread.
  • Monitor: an unlock happens-before every later lock of the same monitor.
  • Volatile: a write happens-before every later read of the same variable.
  • Thread start: t.start() happens-before anything in t.
  • Thread end: everything in t happens-before another thread returns from t.join().
  • Interrupt: t.interrupt() happens-before t detecting it.
  • Final fields: the end of a constructor happens-before any read of the object's final fields through a properly published reference.
  • Transitivity: A → B and B → C gives A → C.

The java.util.concurrent classes add their own: putting into a BlockingQueue happens-before taking it out, submitting a task happens-before it runs, and a task's completion happens-before Future.get() returns.

What is safe publication? Name four ways to do it.
Model answer

Making an object's reference and its fully constructed state visible to other threads together. Ways to do it:

  1. Initialise it from a static initialiser.
  2. Store the reference in a volatile field or an AtomicReference.
  3. Store it in a final field of a properly constructed object.
  4. Store it in a field guarded by a lock, or in a thread-safe collection.

Also: don't let this escape during construction, for example by starting a thread or registering a listener from the constructor.

What is false sharing and how do you fix it?
Model answer

Two threads write to different variables that happen to sit on the same 64-byte cache line. Each write invalidates the other core's copy, so the line ping-pongs between cores and performance collapses even though there's no logical sharing. Fix with padding, @jdk.internal.vm.annotation.Contended (used inside the JDK, e.g. in LongAdder's cells), or by giving each thread its own data and combining at the end.

Section 5

Executors and thread pools

What problem does the Executor framework solve? Name its main interfaces.
Model answer

It separates submitting a task from how and when it runs, so you can change the execution policy (pool size, queue, rejection) without touching the calling code, and stop creating a thread per task. Interfaces: Executor (execute(Runnable)), ExecutorService (adds submit, invokeAll/invokeAny and lifecycle), and ScheduledExecutorService (delays and periodic tasks).

Name the seven constructor parameters of ThreadPoolExecutor.
Model answer

corePoolSize, maximumPoolSize, keepAliveTime, unit, workQueue, threadFactory (names, daemon flag, uncaught-exception handler) and handler (the rejection policy). Also useful: allowCoreThreadTimeOut(true) and prestartAllCoreThreads(). Recall the order execute() uses them: core threads, then the queue, then extra threads up to max, then reject.

Compare the pool types from Executors. Which would you use in production?
Model answer
  • newFixedThreadPool(n): n threads with an unbounded LinkedBlockingQueue. Risk: the queue grows until memory runs out.
  • newCachedThreadPool(): 0 to unlimited threads with a SynchronousQueue and a 60 s keep-alive. Risk: unbounded threads.
  • newSingleThreadExecutor(): sequential execution, and it replaces the thread if it dies.
  • newScheduledThreadPool(n): delayed and periodic tasks.
  • newWorkStealingPool(): a ForkJoinPool with one queue per worker.
  • newVirtualThreadPerTaskExecutor(): one virtual thread per task (Java 21).

In production, construct ThreadPoolExecutor directly with a bounded queue, named threads and an explicit rejection policy, and expose its metrics (active count, queue size).

Why is ScheduledThreadPoolExecutor preferred over java.util.Timer?
Model answer
  • Timer has a single thread, so one slow task delays all the others.
  • An uncaught exception in a TimerTask kills that thread, and the Timer is then dead: later scheduling throws IllegalStateException.
  • Timer schedules on the wall clock, so changing the system clock shifts tasks.

ScheduledThreadPoolExecutor can use several threads and measures time with nanoTime. An exception only cancels future runs of that one task, and it shows up in the task's ScheduledFuture.

Runnable vs Callable, and what Future gives you.
Model answer

Runnable.run() returns nothing and can't throw checked exceptions. Callable.call() returns a value and can throw. submit returns a Future, with get() and get(timeout) (exceptions arrive wrapped in ExecutionException), cancel(mayInterrupt), isDone() and isCancelled(). A plain Future can't be composed or completed from outside; CompletableFuture adds both.

What is a CompletionService, and when do you need one?
Model answer

ExecutorCompletionService wraps an executor and puts each finished Future on an internal BlockingQueue. take() then returns results in completion order rather than submission order. Use it when you fire N tasks and want to handle each result as soon as it's ready, or stop after the first K. Looping over a list of Futures calling get() blocks on the slowest task first.

How do exceptions behave in a thread pool, and how do you make sure none go unnoticed?
Model answer

With execute(), the exception reaches the thread's UncaughtExceptionHandler (the default prints it) and the worker thread is replaced. With submit(), it is captured in the Future and is lost if no one calls get(). Options:

  • Always check your Futures.
  • Override afterExecute(r, t) and unwrap the Future there.
  • Wrap tasks in a try/catch that logs.
  • Set a handler in the ThreadFactory.
How does ForkJoinPool differ from ThreadPoolExecutor?
Model answer

Each worker has its own deque. It pushes and pops its own subtasks from one end (LIFO, cache-friendly), and idle workers steal from the other end of busy workers' deques. A task that calls join() runs other queued tasks while it waits, so recursive divide-and-conquer doesn't cause the pool-induced deadlock a fixed pool would. It's the backing pool for parallel streams, for CompletableFuture's default async executor (commonPool, about cores − 1 threads) and for virtual-thread carriers. It's a bad fit for blocking I/O.

How do virtual threads work, and what is pinning?
Model answer

A virtual thread is a heap-allocated continuation that the JVM mounts on a small pool of carrier OS threads (a ForkJoinPool). When it blocks on I/O, a lock, sleep or a queue, the JVM saves its stack to the heap and frees the carrier for another virtual thread, so millions of mostly-blocked tasks are cheap. Pinning is when it can't unmount: inside native frames, and on JDK 21–23 inside synchronized blocks (fixed in JDK 24 by JEP 491). A pinned blocking call holds the carrier, and with enough of them the program stalls. Don't pool virtual threads; bound resources with a Semaphore instead.

Write the standard graceful-shutdown sequence for an ExecutorService.
Model answer
pool.shutdown();                                   // stop accepting new tasks
try {
  if (!pool.awaitTermination(30, TimeUnit.SECONDS)) {
    pool.shutdownNow();                            // interrupt running tasks
    if (!pool.awaitTermination(10, TimeUnit.SECONDS))
      log.error("pool did not terminate");
  }
} catch (InterruptedException e) {
  pool.shutdownNow();
  Thread.currentThread().interrupt();
}

Since Java 19, ExecutorService is AutoCloseable, and close() does the first half for you.

Section 6

Utilities, ThreadLocal and concurrent collections

CountDownLatch vs CyclicBarrier vs Phaser?
Model answer
  • CountDownLatch: one-shot. Any threads count down; waiters are released at zero. It can't be reset. Typical uses: waiting for N services to start, or a start gun for a test.
  • CyclicBarrier: N parties wait for each other, then all proceed; it resets for the next round. It has an optional barrier action run by the last thread to arrive. If one party is interrupted or times out, the others get BrokenBarrierException.
  • Phaser: a reusable barrier where the number of parties can change (register and deregister), with multiple phases. Use it when the set of participants changes over time.
How is ThreadLocal implemented, and why does it leak in thread pools?
Model answer

Each Thread holds a ThreadLocalMap whose keys are weak references to the ThreadLocal objects and whose values are strong references. In a pool, threads live forever, so:

  1. A value set by one task is still there for the next task. That leaks data between requests, for example a user ID.
  2. The values are never garbage-collected.

Always remove() in finally. Alternatives: pass context explicitly, or use ScopedValue (final in JDK 25), which is bound to a block of code and suits virtual threads.

How does ConcurrentHashMap (Java 8+) achieve concurrency? Why doesn't it allow null?
Model answer
  • Reads take no lock: they are volatile reads of the table and the nodes.
  • Writes CAS a new node into an empty bin, and otherwise synchronized on the bin's first node, so writers only contend when they hit the same bin.
  • Bins with long chains become red-black trees.
  • Resizing is shared: threads that write during a resize help move bins.
  • size() sums striped counter cells, like LongAdder.

No nulls, because get(k) == null must unambiguously mean “absent”. With concurrent writers you can't follow it with containsKey to disambiguate.

Collections.synchronizedMap vs ConcurrentHashMap?
Model answer

synchronizedMap wraps every method in one lock: it's simple but all operations are serialised, and you must hold the lock manually while iterating or you get ConcurrentModificationException. ConcurrentHashMap lets operations run in parallel, its iterators are weakly consistent (no exception; they may or may not see concurrent updates), and it has atomic compound operations (putIfAbsent, compute, merge).

When is CopyOnWriteArrayList the right choice?
Model answer

When reads and iteration vastly outnumber writes, for example a listener list or a routing table updated rarely. Every write copies the whole array, and readers iterate over an immutable snapshot with no locking. For write-heavy workloads it's terrible, O(n) per write.

Which BlockingQueue implementation would you choose, and why?
Model answer
  • ArrayBlockingQueue: bounded, one lock, no allocation per item.
  • LinkedBlockingQueue: optionally bounded, separate put and take locks, so producers and consumers contend less.
  • SynchronousQueue: zero capacity; every put waits for a matching take.
  • PriorityBlockingQueue: unbounded, ordered.
  • DelayQueue: items become available only after their delay expires.
  • LinkedTransferQueue: producers can wait until a consumer receives the item.

Other concurrent collections: ConcurrentSkipListMap is a sorted, lock-free map, and ConcurrentLinkedQueue is a non-blocking queue.

Section 7

Atomics and lock-free programming

What is CAS, and what does a CAS retry loop look like?
Model answer

Compare-and-swap is a single CPU instruction: set a memory location to a new value only if it still holds the expected value, and report whether it did. Lock-free algorithms read the current value, compute a new one, attempt the CAS, and retry on failure:

int prev, next;
do {
  prev = value.get();
  next = Math.max(prev, candidate);
} while (!value.compareAndSet(prev, next));

This is exactly what value.accumulateAndGet(candidate, Math::max) does.

What is the ABA problem?
Model answer

Thread 1 reads A and gets delayed. Thread 2 changes the value to B and back to A, perhaps freeing and reusing a node. Thread 1's CAS succeeds because it still sees A, but the structure underneath has changed; in a lock-free stack this corrupts the list. Fixes: a version stamp (AtomicStampedReference), or relying on garbage collection so a node can't be reused while someone still holds a reference. That's why ABA is much rarer in Java than in C++.

AtomicLong vs LongAdder?
Model answer

Under heavy contention, AtomicLong's CAS keeps failing and retrying on one cache line. LongAdder spreads updates across padded cells, typically one per contending thread, and sum() adds them up. Increments scale far better, but sum() is not an atomic snapshot and there's no compareAndSet. Use LongAdder for counters and metrics, and AtomicLong for sequence numbers or anything that needs CAS.

Blocking vs lock-free vs wait-free?
Model answer

Blocking: a thread paused while holding a lock can stop everyone. Lock-free: some thread always makes progress, though an individual thread may retry forever. Wait-free: every thread finishes in a bounded number of its own steps. Wait-free is the strongest and hardest to build. Lock-free doesn't automatically mean faster: under high contention a well-designed lock can win.

Section 8

Go concurrency

Explain Go's G-M-P scheduler.
Model answer
  • G is a goroutine: a small, growable stack starting at about 2 KB.
  • M is an OS thread.
  • P is a logical processor holding a local run queue. There are GOMAXPROCS of them.

An M must hold a P to run Gs. Idle Ps steal Gs from other Ps' queues. When a G makes a blocking syscall, its M gives up its P so another M can keep running Gs. Network I/O goes through the netpoller (epoll or kqueue), so goroutines waiting on sockets don't hold threads at all. Since Go 1.14 the runtime can preempt long-running goroutines asynchronously.

A useful trick: set a channel variable to nil to disable its case in a select. Rule of thumb: only the sender closes, and only when there is exactly one sender (or a coordinator that knows every sender is done).

When should you use a mutex instead of a channel in Go?
Model answer

Use channels to transfer ownership of data or to coordinate stages (pipelines, fan-out and fan-in, signalling completion). Use a mutex to protect shared state that many goroutines read and update in place, like a cache or a counter. Forcing state through a channel owned by one goroutine works, but it's often slower and more code. “Share memory by communicating” is guidance, not a rule.

What is context.Context for, and what are the rules for using it?
Model answer

It carries cancellation, deadlines and request-scoped values across API boundaries and goroutines. Rules:

  • Pass it as the first parameter.
  • Never store it in a struct.
  • Always call the cancel function you get back, usually with defer, or you leak timers.
  • Blocking operations should select on ctx.Done().
  • Put only request-scoped data in values (a trace ID), never optional parameters.

Cancellation flows down the tree: cancelling a parent cancels every child.

What do sync.Once, sync.Pool and sync.Cond do, and when would you avoid them?
Model answer
  • Once: runs an initialiser exactly once; concurrent callers wait for it. Go 1.21 added sync.OnceValue.
  • Pool: a cache of reusable temporary objects (buffers) that reduces GC pressure. Items can be dropped at any GC, so it's not a connection pool.
  • Cond: a condition variable. It's rarely the right choice because it can't be combined with select or context cancellation; channels usually express the same thing better.
What causes goroutine leaks, and how do you find them?
Model answer

A goroutine blocked forever: sending on a channel nobody reads (the classic timeout-then-return case), receiving on a channel nobody closes, or waiting on a mutex or WaitGroup that is never released. Find them by watching runtime.NumGoroutine in metrics, reading /debug/pprof/goroutine?debug=2 grouped by stack, and running go.uber.org/goleak in tests. Prevent them by giving every goroutine a clear exit condition: a context, a closed channel, or a buffered result channel.

What does the Go memory model say about data races?
Model answer

Synchronisation (channel operations, mutexes, sync/atomic, Once, WaitGroup) creates happens-before edges. A send happens-before the matching receive completes, and closing a channel happens-before a receive that sees it closed. A program with a data race has no guarantees for the racing reads. Racy reads of multi-word values like strings, slices and interfaces can see torn values and crash. Run go test -race in CI.

Section 9

Senior-level design questions

Optimistic vs pessimistic concurrency control: when do you choose each?
Model answer

Pessimistic: lock before touching the data (SELECT … FOR UPDATE, a mutex). Best under high contention, where retries would be wasted work. Optimistic: read a version, do the work, then write only if the version is unchanged (a CAS, UPDATE … WHERE version = ?, an ETag with If-Match), and retry on conflict. Best when conflicts are rare and holding locks across slow operations or network calls is expensive.

Why are distributed locks dangerous, and what is a fencing token?
Model answer

A client can hold a lease-based lock, pause (a GC pause, a network delay), let the lease expire and then keep writing while another client also believes it holds the lock. A fencing token is a number that increases every time the lock is granted. The storage layer rejects writes carrying a token lower than the highest it has already seen, so the stale holder's writes fail. Without fencing, a lock only makes conflicts less likely; it doesn't guarantee safety.

What are the backpressure strategies when producers outpace consumers?
Model answer
  • Block the producer: a bounded queue with put.
  • Reject quickly: offer or AbortPolicy, then return HTTP 429 or 503.
  • Slow the caller: CallerRunsPolicy.
  • Drop: newest or oldest, which suits metrics and telemetry.
  • Buffer to disk: for example Kafka.
  • Adapt: shrink the concurrency limit using AIMD.

The one wrong answer is an unbounded in-memory queue, which only postpones an out-of-memory failure and hides the latency until then.

How do you test concurrent code?
Model answer
  • Stress tests: many threads, many iterations, and invariant checks (totals conserved, nothing lost or duplicated).
  • Start gates: release all threads at once with a CountDownLatch to maximise overlap.
  • Deterministic interleavings: force specific orders with latches or hooks in the code.
  • Specialised tools: Java's jcstress for memory-model effects, Lincheck for linearizability, and Go's -race with -count.
  • Test the tests: they must fail on a deliberately broken version.
A service hangs in production. Walk through how you'd diagnose it.
Model answer
  1. Check CPU. Near 0% suggests a deadlock or waiting on I/O; 100% suggests a hot loop or livelock.
  2. Take 2–3 thread dumps (jstack, jcmd Thread.print) a few seconds apart. Look for “Found one Java-level deadlock”, many threads BLOCKED on one monitor, or threads WAITING on a pool, queue or connection pool.
  3. For a lock, find which thread owns it and what that thread is doing.
  4. Check pool metrics: active threads, queue depth, rejections.
  5. In Go, use the goroutine profile from pprof, or SIGQUIT to dump every goroutine's stack.
  6. Fix the cause (lock ordering, timeouts on every blocking call, separate pools per dependency), then add a metric or alert so the next time is caught early.
